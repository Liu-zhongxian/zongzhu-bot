## 1. 本次完成了什么

把已有的“宗主”ESP32 语音助手变成 Grok Bot 的语音入口：用户唤醒板子后直接说话，本机后端将语音识别为文字，通过 Webhook 送到已有 Grok Bot 的“硬件”对话，由 Bot 接收和处理。

最终方案按用户要求调整为：所有识别到的普通对话都发给 Grok Bot，不需要“让机器人”前缀。板子先播报提交回执，等待 Bot 回传后朗读正文并显示字幕，读完保留完整文字；完整版也保留在电脑上的原 Bot 对话。

实机验收语句为“请回复宗主测试成功”。后端完整识别、板子播报提交成功，Grok Bot 原对话回复“宗主测试成功”，三处证据相互对应。

## 2. 目标与方案选择

用户需要的是“对板子说话，让已有的 Grok Bot 接收任务”。因此改用用户提供、由既有例行任务接收的 Webhook。入口为“硬件”Bot 下的“ESP32 板子命令”。实测鉴权方式为 `Authorization: Bearer <token>`，成功返回 HTTP 200、`success: true` 与 `runUuid`。Bot 早先给出的 HMAC 说明与该入口不一致，最终实现以实测为准。

继续使用现成的小智语音后端处理录音、识别和语音合成，初次接入时无需更换固件。之后为改善等待与圆屏显示，已升级到 2.5.2.3（第 13 节）。

## 3. 最终工作流程

```text
用户说“你好宗主”或按键
  → 板子开始聆听，用户说出需求
  → ESP32 通过局域网 WebSocket 上传语音
  → 本机 FunASR 识别文字 → HTTPS Webhook 提交给 Grok Bot
  → 板子播报提交回执 → 显示等待秒数、暂停普通收音
  → Bot 处理并将实际回复写入约定的本机 JSON 文件
  → 后端校验并发送全文预览、EdgeTTS 音频与分句字幕
  → 板子朗读结束进入待机，保留完整正文供查看
```

“任务已提交”表示入口接受请求，不等于已经执行完成。等待超过默认 300 秒仍保留 pending，不自动重发；下次连接可补送。若希望追加或开始下一轮，重新唤醒或按键。完整回复只保留在板子内存中，不跨板子重启保存。

## 8. 日常使用与维护

唤醒后等唤醒回应说完，再说完整需求。聆听期间所有识别到的普通话语都会转发，因此“好”等短句也会成为 Bot 消息。提交后进入等待，暂停普通收音；回复会在板子朗读并显示，读完保留全文。下一轮重新唤醒或按键。完整版和任务实际执行结果仍可在原“硬件”对话查看。

## 11. 历史阶段：Bot 回复回传板子屏幕（2026-10-15）

本节保留当时的实现与验收，当前版本已增加朗读和等待收音控制，见第 13 节。

### 11.1 回传方式（20:21–20:30 新增）

开启回传后（私有 JSON 中设置 `reply_dir`），后端每提交一条任务，会先在 `private/bot-replies/` 建立 `<request_id>.pending.json`，记录请求编号和设备 MAC。发给 Bot 的消息中附带约定：Bot 回复用户后，用本机文件能力在 Mac 上写入 `<request_id>.json`（`{"request_id", "text"}`）。后端每秒检查该目录，校验编号、设备、大小与符号链接后，以 `tts / sentence_start` 消息把文字发给板子显示，再将 pending 改名为 `.sent.json`。板子提交回执相应变为“任务已提交，Bot 回复后会显示在屏幕上”。

| 文件 | 作用 |
| --- | --- |
| `core/handle/grokBotReply.py` | 建立 pending、读取校验回复、推送屏幕、等待期间保持连接。 |
| `core/handle/grokBotHandle.py` | 提交时建立 pending，并在 Bot 消息中附回传约定。 |
| `core/handle/helloHandle.py` | 设备连接（hello）后启动回复监视。 |
| `tests/test_grok_bot_reply.py` | 9 项单元测试。 |
| `verify_bot_reply.py` | 模拟设备的真实 Bot 往返测试，会真实触发一条 Bot 任务。 |

当时的往返记录：模拟设备 `ESP32-cb88…` 于 20:27:32 收到回复（`logs/bot-reply-check.json`，耗时 43 秒）；实体板 `ESP32-ae4a…` 于 20:29:35 推送“宗主屏幕回传成功。”。

### 11.2 发现的问题：回复晚到时板子已断线

板子与后端的 WebSocket 不是常连：后端在 120 秒无语音后会关闭连接，板子固件也会在 120 秒没有收到任何下行消息后自行断开；断开后板子待机，后端无法主动唤醒它。Bot 回复通常要几十秒到几分钟，常常晚于断开时间。

实际案例：`ESP32-a141…` 在 20:29:55 提交，板子 20:29:59 断开，Bot 20:30 写好回复，但该回复一直停在 pending，没有送达。

### 11.3 修复（只改后端，不改固件）

- **等待期间保持连接**：只要这块板子还有未送达、且提交不超过 `reply_wait_seconds`（默认 300 秒，可在私有 JSON 中修改）的请求，回复监视就持续刷新后端的空闲计时，使两种后端超时都不触发；同时每 30 秒向板子发送一条 `{"type": "bot_wait"}`，避免固件 120 秒无下行消息自行断开。固件对未知类型只记录警告并忽略，但仍算作收到数据。
- **超时或手动断开后的补送**：如果超过等待时限，或用户按键/唤醒词主动结束对话，回复会保留在 pending，下次唤醒连接时再送达。这类上一次会话留下的回复，显示时会加上“稍早的 Bot 回复：”前缀。上述 `ESP32-a141…` 会在下次唤醒时这样显示。
- 回复送达或等待超时后，连接恢复原来的空闲断开规则。

改动前代码备份：`backups/grokBotReply-before-hold-20261015.py`、`backups/test_grok_bot_reply-before-hold-20261015.py`。修改后已于 20:54 重启后端，PID 记录在 `logs/grok-server.pid`。

### 11.5 当时的使用影响与限制（部分已由第 12–13 节解决）

- 实测中，一句较长的话在停顿处被拆成了两条任务分别提交（VAD 静音断句 700ms）。说长句时尽量不要中途停顿。
- 等待回复期间板子保持“聆听”状态，麦克风一直开着，期间说的话都会作为新的 Bot 任务提交，最长持续 `reply_wait_seconds`。不想等待时可按键或说唤醒词结束，回复会在下次唤醒时显示。
- 该阶段回复只显示文字、不朗读；1.75 寸圆屏能显示的字数有限，较长的回复需要回原 Bot 对话查看。
- 回传能否成功取决于 Bot 是否按约定把文件写到 Mac 本机。Bot 写错位置或格式时，回复不会显示，只能在原对话查看。
- 后端重启后，旧连接上的等待随之结束；pending 文件仍保留，设备重新连接后可以继续补送。

## 12. 历史阶段：2026-10-16 首次加入正文语音朗读

本节记录加入朗读时的行为；2.5.2.3 已将朗读结束后的“恢复聆听”改为“待机并保留全文”，见第 13 节。

### 改动

在现有回传逻辑上复用 `speak_txt()` 与 EdgeTTS 队列：回复到达后，先确认板子没有播报、用户没有讲话、唤醒回复已经结束且 TTS 已初始化，再建立新的 sentence_id，切换到说话状态并显示完整正文预览。随后播放合成音频、推送分句字幕，由已有 TTS 逻辑发出 stop，恢复聆听。没有更换固件。

正在朗读本轮 Bot 回复时，回复监视器继续保持连接，避免长回复因空闲计时被切断。用户打断仍走原有 abort 路径；如果播放启动时已经被用户打断，不会再将正文放入队列。投递失败会保留 pending 并恢复说话状态；已投递到队列的回复不会自动重播。sent 状态不代表已获得板子播放完成确认。

主要文件：`core/handle/grokBotReply.py`、`tests/test_grok_bot_reply.py`。变更前代码保存在 `backups/reply-speech-20261016/`。新增 `verify_bot_speech.py`：真实发送一条无副作用 Bot 测试，分别统计提交提示和正文的音频，解码正文 Opus，验证非静音 PCM、字幕编号和播放结束消息。

## 13. 2026-10-16：等待体验与圆屏显示一起优化

### 用户体验

- 提交提示播放结束后，屏幕进入“等待 Bot”，显示已等待秒数和追加指令的方法。此处是等待时间，不代表 Bot 的实际执行进度。
- 等待时暂停普通语音上传，保留本地“你好宗主”唤醒和按键入口。再次唤醒或按键可以追加指令，同一条未完成任务不会反复把用户拉回等待。
- 默认等待 300 秒；超过时限显示“回复还未到达，请稍后唤醒查看”，保留 pending，不自动重发任务。断线时显示连接已断开的提示。
- 再次开始输入时，已有回复最多暂缓 15 秒，让用户有时间说话；正在讲话或播放时继续沿用原有避让规则。
- 有文字时将 IKUN 缩小至约六成，正文区域从 284×90 扩至 284×160。长内容先停留 2.5 秒，再缓慢滚动，末尾停留 3 秒后回到顶部。清空正文时恢复大动画。
- 回复到达后保持现有分句字幕和正文朗读；朗读结束进入待机并恢复整段正文，便于继续查看。下一轮说话需要唤醒或按键。待机后不再把周围闲聊持续提交给 Bot。

后端只向声明 bot_ui 的设备发送新 UI 消息，旧固件继续原先的语音/字幕行为。主要修改 `grokBotReply.py`、`receiveAudioHandle.py`、`textHandler/listenMessageHandler.py` 和 `grokBotHandle.py`。等待期间后端也丢弃残留收音，防止已在传输中的音频生成新任务。

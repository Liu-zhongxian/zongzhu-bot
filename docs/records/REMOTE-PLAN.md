# 任务说明书：脱离电脑与局域网

创建：2026-10-19（Asia/Shanghai）。状态：**进行中**。2026-10-20：立创实战派已切到服务器，完整对话实机通过（第 8 节「立创板切换记录」）；微雪 1.75C 仍连 Mac。2026-10-19 曾在阶段 5 暂停，见「暂停记录」。

## 1. 目标

现在宗主要求一台常开的电脑，并且板子和电脑在同一个局域网。目标是两条都去掉：

- 电脑关机，宗主照常工作。
- 板子在任何能上网的地方都能用，不限家里的 Wi-Fi。

## 2. 为什么现在离不开电脑

链路里有两处依赖电脑：

| 环节 | 现状 | 问题 |
| --- | --- | --- |
| 语音识别、合成、Bot 桥接 | 后端跑在电脑上，板子用 `ws://局域网IP:8000` 连接 | 电脑关机就断；出了局域网连不上 |
| Bot 回传 | Bot 用 Mac 本机能力把回复 JSON 写到电脑上的 `reply_dir` | 即使后端搬走，回复也只会落在 Mac 上 |

后端搬到服务器是常规部署工作。真正决定方案的是第二处：Bot 能不能不经过 Mac，把回复直接发给服务器。

## 3. 已验证的事实

| 日期 | 事实 | 依据 |
| --- | --- | --- |
| 2026-10-19 | Bot 执行任务的环境是**云端 Linux 虚拟机**（主机名形如 `grok-bot-vm-*`，x86_64），不是用户的 Mac | 在 Bot 对话里执行 `hostname; uname -a` |
| 2026-10-19 | 该虚拟机可以主动访问外网 HTTPS，curl POST 到 httpbin.org 正常返回 | 同上，`curl -X POST https://httpbin.org/post` |
| 2026-10-19 | 虚拟机出口 IP 每次可能变化，**不能用 IP 白名单**做鉴权 | 云虚拟机特性，鉴权改用一次性令牌 |
| 2026-10-17 | 国内云函数（上海）可以访问 Bot 的 Webhook 入口，Bot 也能回调云端地址 | 早期 CloudBase 实验，未切换正式链路 |

结论：Bot 可以用 HTTPS 把回复 POST 到服务器，**整条链路可以完全不经过电脑**。

## 4. 目标架构

```
板子（任何网络）──wss──▶ 域名 ──▶ 服务器反向代理（自动 HTTPS）──▶ 后端容器
                                                              │ FunASR 识别
                                                              │ Bot 桥接 ──HTTPS──▶ Grok Bot Webhook
                                                              │ EdgeTTS 合成
Bot 云端虚拟机 ──HTTPS POST /bot/reply（一次性令牌）──▶ 域名 ──▶ 后端容器
```

反向代理只放行三个路径，其余一律返回 404：

| 路径 | 转发到 | 用途 |
| --- | --- | --- |
| `/xiaozhi/v1/` | 8000 | 板子的 WebSocket |
| `/xiaozhi/ota/` | 8003 | 板子开机取配置 |
| `/bot/reply` | 8003 | Bot 回传 |

## 5. 已完成：HTTPS 回传（2026-10-19）

| 文件 | 改动 |
| --- | --- |
| `core/api/bot_reply_handler.py` | 新增 `POST /bot/reply`；请求体上限 64KB；未配置 `reply_url` 时返回 503 |
| `core/handle/grokBotReply.py` | 新增 `accept_reply()`：校验 `request_id` 格式、令牌、正文长度，原子写入回复文件；pending 文件只保存令牌的 SHA-256 |
| `core/handle/grokBotHandle.py` | 配置了 `reply_url` 时，为每个任务生成一次性令牌，并让 Bot 用 curl 回传；`reply_url` 必须是 HTTPS |
| `core/http_server.py` | 注册路由 |
| `examples/grok-bot-webhook.example.json` | 新增 `reply_url`，留空则保持原来的写文件方式 |

设计要点：

- 回传接口把收到的回复转存成和原来完全相同的回复文件，所以等待倒计时、断线补发、超时保留这些现有逻辑都没有改。
- 令牌每个任务一个，只能用一次（第二次返回 409），24 小时后失效。令牌对不上返回 403，任务不存在返回 404。
- Webhook 的长期密钥不会出现在发给 Bot 的指令里。

验证：后端测试 37 项通过，其中新增 9 项覆盖回传接口。**尚未用真实 Bot 跑过 HTTPS 回传。**

## 6. 部署位置

用户有一台服务器和一个域名（目前未绑定），也有一台 NAS。优先用服务器：

| 选项 | 评价 |
| --- | --- |
| **服务器**（首选） | 有公网 IP，延迟最低，最省事 |
| NAS + Cloudflare Tunnel | 备选。不用公网 IP，但国内访问会多 100–300ms，且依赖家里网络 |

服务器在**中国大陆**时要注意：

- 域名解析到大陆服务器、走 80/443 端口，需要 **ICP 备案**，没备案会被拦截。
- 要实测服务器能否访问 Grok Bot 的 Webhook 和 EdgeTTS。早期上海云函数能访问 Webhook，但普通云服务器的网络环境不一定一样。

服务器在香港或海外时，以上两条都不是问题。

### 暂停记录（2026-10-19）

用户要求暂停。暂停时的状态：

| 项目 | 状态 |
| --- | --- |
| 板子 | OTA 地址未改，仍为 `http://192.168.124.158:8003/xiaozhi/ota/`；没有进入配网模式，Wi-Fi 设置未动 |
| Mac 后端 | 照常运行（端口 8000、8003）。原先在用户终端前台运行的进程中途被停过，现由 `start.sh` 在后台重新启动，日志 `logs/backend-restart-20261019.log`（本机，不在仓库） |
| 服务器 | 照常运行，与板子互不影响 |

已经尝试过的方法：

1. **启动时单击 BOOT**：串口日志显示，只有重启后约 1.8–3.5 秒（`starting` 状态，连上 Wi-Fi 之前）单击才有效，窗口约 1.7 秒。
   - 第一次：用户看到屏幕亮起再点，点击在约 26 秒时才被识别，变成了开始对话。
   - 第二次：用户先开始连续点击，再由串口复位，日志里没有识别到点击，板子直接连上了 Wi-Fi。
   - 结论：靠手按时机不可靠。
2. **由后端调用设备工具 `self.system.reconfigure_wifi`**：写了一个临时替身程序，在 8003 下发 OTA、在 8000 接受板子连接，板子一开始对话就发送 MCP `initialize` 和 `tools/call`。替身需要占用 Mac 后端的端口，所以先停了 Mac 后端。启动替身时用户要求暂停，替身**没有真正运行过**。之后已关闭替身，并恢复 Mac 后端。

恢复时的建议：

- 优先用方法 2，不依赖手速。流程：停 Mac 后端 → 启动替身 → 对板子说「你好宗主」或单击一次 BOOT 开始对话 → 板子进入配网模式 → 关掉替身、恢复 Mac 后端 → 连板子热点改 OTA 地址。
- 更省事的长期做法：在服务端加一个管理入口，可以按需给已连接的设备下发 `self.system.reconfigure_wifi`，以后切换地址不用再停后端。

### 等待授权提醒（2026-10-20，仅服务端）

Bot 有时要在 Grok 界面请求授权才执行脚本，这个请求服务器看不到，也没法转给板子。改为：等待超过 `approval_hint_seconds`（Webhook 配置，默认 30，0 关闭）后，服务器用 `tts sentence_start` 把屏幕正文换成「等待时间较长。如果 Grok 界面在请求授权，请在那里确认。」状态栏照常计秒；每个任务提醒一次，唤醒追加时不提醒。不需要重刷固件。本项目 43 项测试通过（新增 2 项）。2026-10-20 11:31 部署到服务器；同日实测时 Bot 没有请求授权，提醒未触发，实机效果留待以后验证。

### 待做：回复到达后自动接收（记录，未实施）

现状：待机时板子没有 WebSocket 连接，只有唤醒或按键才连。开机只请求一次 HTTPS OTA，服务器无法借此推送。所以以下两种情况要用户先说「你好宗主」才能听到回复：

1. 等待期间断电或断网，回复在离线时到达，重新上电后。
2. 等待超过 `reply_wait_seconds`（默认 300 秒）后板子断开，之后才到达的回复。

方案（需改固件，两块板都要重刷）：

- **开机检查**：服务器 OTA 响应增加字段（例如 `bot_pending: true`），条件是该设备（MAC + client-id）有未投递的回复。固件激活完成后看到这个字段，自动打开音频通道接收并朗读，不用唤醒词。
- **超时后轮询**：显示「回复还未到达」后，固件每隔约 60 秒请求一次 OTA（或一个更轻的查询接口），看到 `bot_pending` 就自动连接；收到回复或超过上限（例如 30 分钟）后停止轮询。
- 自动连接时不播放唤醒问候，也不进入收音，直接接收回复；朗读结束后回到待机。
- 公网部署下，查询接口沿用设备白名单，只回答「有/没有」，不返回回复内容。

## 9. 风险

| 风险 | 应对 |
| --- | --- |
| 一次性令牌出现在 Bot 对话里 | 令牌只对这一个任务有效、只能用一次、24 小时失效，泄露的影响限于伪造这一条回复 |
| 后端暴露公网后被滥用 | 反向代理只放行三个路径；后端开启设备白名单（`server.auth`） |
| 大陆服务器访问不到 Webhook 或 EdgeTTS | 阶段 1 先测；不通则换香港服务器，或者 TTS 换国内服务 |
| 公网延迟比局域网高 | 阶段 6 实测；音频本来就是流式传输，预计影响在几百毫秒内 |

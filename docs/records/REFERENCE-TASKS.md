## 3. 第 1 项：提交回执即时出声

**问题。** 说完话后要等 Webhook 返回才合成并播报"任务已提交"，实测约 3 秒（任务记录第 15.2 节）。其中 EdgeTTS 联网合成约 2 秒，Webhook 约 1–3 秒。

**做法。**

- 新增 `core/handle/grokBotPhrases.py`：固定短句（"好的，正在交给 Bot。""我在。"）合成一次后，音频按 TTS 类型、音色、采样率、文字缓存在内存。板子连上后在后台预先合成，之后直接发出缓存的 Opus 包，不走 TTS 队列。
- `grokBotHandle.py` 拆成两段：先做检查（空指令、过长、配置、去重、回传目录），不通过就直接播报原因，不提交；通过后**同时**播报回执和发 Webhook。
- Webhook 成功：不再说第二句，屏幕进入等待秒数。失败（4xx）：先让屏幕退出等待，再播报"任务未提交"的原因。结果不确定（超时、返回格式不对）：播报原有的"暂时无法确认……"，保留等待。
- 缓存还没就绪时（服务刚启动、合成失败），退回原来的实时合成，行为与以前一致。

**提示语的变化。** 以前成功后说"任务已提交，Bot 回复后会显示在屏幕上"；现在一开口就说"好的，正在交给 Bot"，这时 Webhook 还没返回，所以不说"已提交"。提交失败时会在回执之后补一句失败原因。

## 4. 第 2 项：开机自启与健康检查

**问题。** Mac 重启后后端没有自动启动，板子取 OTA 失败，回退到旧的官方 MQTT（任务记录第 17 节）。

**做法。** 新增 `tools/autostart.sh`（macOS launchd，用户级）和 `tools/launcher.c`：

| 命令 | 作用 |
| --- | --- |
| `enable` | 编译启动器 `~/Applications/ZongzhuBackend.app`，写入 `~/Library/LaunchAgents/com.zongzhu.backend.plist`，登录后自动启动，进程退出后自动拉起；马上启动并等 OTA 接口可访问 |
| `disable` | 停止服务并删除自启文件 |
| `restart` | 重启后台服务（更新代码、改配置后） |
| `status` | 自检：自启是否开启、指向哪份安装；8000/8003 是否在监听；OTA 是否返回；`.config.yaml` 里的 WebSocket 地址是否是本机当前局域网 IP；Webhook 配置是否存在且权限为 600 |

- 后端运行期间启动器同时运行 `caffeinate -i -w <后端进程>`，Mac 不会因为空闲而睡眠（合盖仍会睡眠）；后端退出时它也结束。
- 日志：`logs/backend.stdout.log`、`logs/backend.stderr.log`。
- 一个用户只有一份自启文件；`status` 会提示它是否指向当前目录。

**macOS 隐私权限。** 仓库放在"桌面""文稿""下载"里时，launchd 直接启动的 bash 会被系统静默拒绝（2026-10-21 实测：`start.sh: Operation not permitted`，不弹窗）。所以 launchd 启动的是一个很小的启动器应用"宗主后端"（`tools/launcher.c`，ad-hoc 签名），由它运行 `start.sh`：第一次访问这些目录时系统会弹窗询问，点"允许"即可，以后不再询问。启动器源码不变就不重新编译，已给的授权一直有效。点了"不允许"时，到"系统设置 → 隐私与安全性 → 文件与文件夹 → 宗主后端"打开，再运行 `restart`。

`web/install-mac.sh` 最后让用户在"1) 开机自启"和"2) 手动启动"之间选择，没有默认项，不回答会一直问；没有可交互的终端时按手动处理。选手动的以后随时可以运行 `tools/autostart.sh enable`。已经开着自启时，重复运行（即更新）直接重启后端，不再询问。

### 7.1 实机测试后的两处修复（2026-10-22）

- **连说几段被提交成几个任务。** 实测连着说了三段，提交了三次。原因：等待状态只在"没人说话、板子也没在出声"的空隙里生效，连续说话时一直等不到。改为提交成功（且板子支持等待界面）后马上停止普通收音（`grokBotHandle.py`）；唤醒或按键照旧恢复，被拒绝或收到回复时照旧退出等待。
- **回复朗读偶尔停顿。** EdgeTTS 一句一句串行合成，每句约 2 秒；短句（如"收到"）播完下一句还没好就会停一下。改为处理当前一句时，按同样的断句规则推算后面两句，交给后台线程先合成（`tts/base.py` 的 `PREFETCH_AHEAD`）；推算不中或后台失败时照旧现合成。`tests/test_tts_prefetch.py` 验证每句只合成一次、顺序不变、后两句与第一句同时开始。

## 8. A1、A2：直接读 Bot 对话拿回复

**问题。** 现在 `grokBotHandle.py` 在发给 Bot 的话后面附一大段回传说明，要求 Bot 做完后把回复写进 `private/bot-replies/`，或者用 curl 回传。回复能不能回来，取决于 Bot 是否照做、云端电脑能不能写到 Mac。Bot 忘了回传、只写了"已完成"、或者停下来问用户时，板子一直等到 300 秒超时，什么也听不到（2026-10-21 新建"演示" Bot 时就遇到过）。

**做法。** 参考 hub-server，后端扮演一个 Grok Bot App：把话直接发进 Bot 的主对话，再从对话记录里读回复，Bot 不需要知道板子的存在。下面文件名都相对于后端目录。

### 8.1 登录与凭证

- 新建 `core/agent/grokbot_client.py`：
  - 登录：用 Cursor 账号走 PKCE，在浏览器里批准后轮询 `/auth/poll` 取 token。
  - 续期：token 到期前 5 分钟用 `/oauth/token` 自动续期，有效期 60 天。
  - 凭证存在 `data/grokbot_credentials.json`，权限 600，日志里永远不打印 token。
- 我们没有管理后台，所以新增 `tools/grokbot_login.py`：打印登录链接，批准后保存凭证。
- 验收：登录成功后日志里有 token 的到期时间，凭证文件权限是 600。

### 8.2 找到要用的 Bot

- 调 `EnsureSandBox` 拿到云端电脑的网关地址（电脑休眠时先叫醒它，最多等 180 秒），再调 `listAgents` 列出所有 Bot。
- 把"硬件"那个 Bot 的 `agentId` 写进私有配置，新增字段 `agent_id`。
- 验收：脚本能列出每个 Bot 的名字、id 和忙闲状态。

### 8.3 事件流

- 移植 `GrokBotHub`，整个账号只开一条 SSE 事件流（`GET {网关}/events`）：
  - 有人订阅时才连上；断线后按 1、2、4、8、10 秒退避重连。
  - 没人订阅 60 秒后关闭。
  - 读取缓冲设为 4MB，否则一条长回复会把流撑断。
- 验收：连上后能收到心跳（`:ping`）；断网再恢复后自动重连，日志里的连接次数递增。

### 8.4 一轮的经过（新文件 `core/handle/grokBotDirect.py`）

1. **发送前**：读一次对话尾部（`getAgentTranscriptTail`），记下已有条目的 id，之后只念新出现的条目。读不到尾部就不发，否则分不清哪些回复是旧的。
2. **发送**：调 `sendPrompt`，带上 `clientNonce`。结果不明确时用 `promptAcceptanceStatus` 查是否送到，不重发。
3. **收回复**：从事件流里依次收到我们这句话的回显、回复条目、Bot 变空闲。每条回复到了就念；先去掉 Markdown 记号，结尾没有句号就补一个，TTS 才会马上念。
4. **判断结束**：
   - Bot 空闲 1.5 秒没有新动静，算这一轮结束。
   - Bot 忙过却一条回复都没来时，多等 5 秒。
   - 消息送到了但 Bot 90 秒一直没反应，念"Bot 没有回话"后结束。
5. **兜底**：
   - 发送 10 秒后还没看到回显，就重连事件流并补拉一次尾部（事件流会"假活"：连着、有心跳，但不推事件）。
   - 等待期间每 12 秒轮询一次（`listAgents` 加尾部）。
   - 推送和轮询按条目 id 去重，谁先到用谁。
6. **Bot 在等审批或提问**（`awaitingUserResponse`）：念"Bot 在等你去 App 里处理"，结束这一轮。
7. 每句话后面附一句语音提示（"回复会被朗读，请口语化、简短"），配置里可以改或关掉。

验收：用假网关写单元测试，覆盖以下情况：正常回复、多条回复、回复被追加、事件流假活、发送结果不明确、Bot 等审批、Bot 不回话。

### 8.5 接回现有的显示与朗读

- 回复走现有的 TTS 朗读和分句字幕。
- 屏幕的 `bot_wait` 状态（waiting、timeout、reply）保持现在的行为，**固件不用改**。
- 热身：设备一连上就在后台叫醒云端电脑并订阅事件流，第一句话不用再等 1～20 秒。
- 验收：用模拟设备跑一遍（参考 `tools/verify` 里等待界面的脚本），再上实体板确认朗读、字幕和读完后保留全文。

### 8.6 模式开关（A2）

- 私有配置新增 `mode: direct | webhook`。
- `direct` 模式下：不再附回传说明；`grokBotReply.py` 的目录轮询只在 `webhook` 模式运行。
- 直连失败（没登录、登录过期、网关连不上）时，要么自动退回 Webhook，要么只念出原因。选哪种见第 13 节问题 2。
- 验收：两种模式各跑一遍，原有后端测试全部通过。

## 9. 两种方案对比：直连登录与 Webhook

| | Webhook（现在） | 直连登录 |
| --- | --- | --- |
| 回复怎么回来 | 靠 Bot 自己多执行一步：写文件或 curl | 后端直接读对话记录 |
| Bot 忘了回传、写错格式、停下来问人 | 板子等到 300 秒超时 | 不会出现：对话里有什么就念什么；等审批时能发现并提示 |
| 多条回复、边写边追加 | 只拿得到写进文件的那一份 | 每条到了就念，追加的部分只念新增的 |
| 有没有送到 | `runUuid` 只说明 Routine 启动了 | 能看到自己这句话的回显，查得到送达状态 |
| 结果不明确时 | 提示用户去 App 里查看；进程内 30 秒去重 | `clientNonce` 加送达状态查询，不重发 |
| 打断或超时以后 | 下次连上时补送（前提是 Bot 回传成功了） | 后台盯着最多 2 小时，做完主动汇报（A3） |
| 实测延迟 | 识别后约 16～22 秒收到回复 | 没在本项目测过 |
| 接口性质 | **官方 Routine Webhook** | **App 内部接口，非官方**；xAI 条款禁止逆向，Cursor 条款禁止抓取 |
| 失效风险 | 低 | 中高：App 升级后接口可能变；服务端以后开始校验客户端签名（`x-cursor-checksum`）就会被拒 |
| 本机保存的凭证 | 一个 Webhook token，只能触发这一个 Routine | Cursor 账号的 token，**相当于整个账号的权限**；泄露的后果大得多 |
| 是否依赖 Mac 路径 | 是（`reply_dir`），或者需要一个公网 HTTPS 回传地址 | 否 |
| 搬到云端（D3） | 回传要改成公网 HTTPS，还可能被 Bot 的 Auto Review 拦下 | 照常可用 |
| 维护 | 小，主要是调回传说明的措辞 | 中，App 升级后要回归测试 |

建议两者结合：默认用直连收发，保留 Webhook 作为后备（A2）。接口失效时板子还能用，平时又不依赖 Bot 自己回传。

## 10. B1、B2：每句开头补播放缓冲

**问题。** 上游只在每轮开头一口气发 5 包（0.3 秒），之后按 60ms 一包匀速发送。Wi-Fi 稍一抖动设备缓冲就被吃空，朗读会断续。这和提前合成是两回事：提前合成解决的是句子之间的停顿，补缓冲解决的是句子中间的卡顿。

**做法**（改 `core/handle/sendAudioHandle.py`，约 30 行）：

- 每发出一包，就更新一次估算的设备播完时间：`play_end = max(play_end, 现在) + 60ms`。
- 发送队列空了（每轮开头，或者上一句发完、下一句才到）时，按 `play_end` 算出设备里还剩几包，把缓冲补到 N 包，之后再匀速发送。只补到 N，不在已有缓冲上再加 N，所以缓冲不会越积越多。
- "播放结束"的等待时间改为按 `play_end` 计算，不再用固定的 `(5 + 2) × 60ms`。
- 新增配置 `tts_audio_prebuffer_count`，默认 15（约 0.9 秒）；配置里没有这一项时沿用上游的 5。

**代价。** 打断后，设备要把已经缓冲的约 0.9 秒播完才停；每轮说完后，也要多等一会儿才开始收音。

**验收。**
- 单元测试：缓冲不会越积越多；两句之间正确补包；打断后清空队列。
- B2：和 `PREFETCH_AHEAD` 一起开，句子之间不停顿、句子中间不卡顿。
- 实机：念一段长回复，中途不再断续；打断时的延迟可以接受。

## 11. A3、A9：长任务

### 11.1 后台继续盯着（依赖 A1）

- 按设备保存，只放内存，24 小时过期，每台设备最多 20 条。

  - 设备在线且空闲（没在说话、没在听、不在一轮里）就马上念，开头说"Bot 做完了：……"。
  - 设备不在线就等下次连上，问候播完约 6 秒后再念。
  - 用户唤醒后先念。
- 要和现有的"稍早的 Bot 回复："补送逻辑合并，避免同一条念两次。
- 验收：
  - 派一个长任务，马上打断，Bot 做完后设备会主动念出结果。

### 14.2 本地指令表

- 新建 `core/handle/localCommandHandle.py`，在 `receiveAudioHandle.py` 调用 `handle_grok_bot` 之前先匹配。命中就在本机执行，回一句缓存好的短句（复用 `grokBotPhrases` 的缓存）；没命中照旧交给 Bot。

| --- | --- |
| 放 / 播放 / 来一首 + 歌名或歌手 | 搜歌，取第一首播放，回"好的，播放〈歌名〉" |
| 暂停 / 停一下 | 暂停 |

### 14.3 音乐源

- 包一层 `core/music/source.py`，提供统一的 `search(keyword)`、`track(id)`、`lyric(id)`。底下接 go-music-dl：它作为单独的 Web 服务运行，后端用 HTTP 调用，接口见 14.8。musicdl 试过，搜索要 7–21 秒，不用。
- 播放地址每次要播时重新请求，不缓存。
- 会员账号的凭证只放在本机私有配置里，权限 600，不进仓库。

### 14.4 在 Mac 上播放（先做）

- 后端管理一个播放器子进程：`ffplay -nodisp -autoexit <地址>`，或者 `mpv --no-video`。暂停和继续用进程信号或者 mpv 的 IPC 控制。先确认本机的 ffmpeg-full 带不带 ffplay，不带就装 mpv。
- 播放器是我们自己的进程，暂停、切歌都完全可控，不依赖 MediaRemote 和系统权限。
- 后端重启时要把播放器一起关掉，不留下孤儿进程。

### 14.5 在板子上播放（以后）

- 用 ffmpeg 把音频转成 Opus，按 60ms 一包推给板子，复用 `play_music` 的通路。
- 歌词按 LRC 时间轴，用 `sentence_start` 字幕消息显示在屏幕上，固件不用改。
- 缺点：板载喇叭音质有限；放音乐期间要靠唤醒词或按键才能打断；B1 补播放缓冲做完后再做这一步更稳。

### 14.7 风险与待定

- **版权和平台条款**：两个工具都走各平台的非官方接口。只限本机自用、用自己的会员账号；不往公开仓库提交音乐文件、账号或 Cookie。
- **许可证**：go-music-dl 是 AGPL-3.0，只作为单独的服务调用，不把代码并进本仓库。
- **局域网暴露**：go-music-dl 监听 `*:8080`，没有只允许本机访问的选项，搜索和下载都不需要登录。常驻之前必须先限制成只有本机能访问。
- **接口会变**：平台改版后工具可能失效，要跟着它们更新。
- **待用户定**（第 13 节问题 6）：只在 Mac 上放，还是也要在板子上放；要不要扫码登录。

**哪些话会被当成本地指令**
- 放歌：说法以"放、播放、来一首、我想听"开头。
- 暂停、继续、停止、"这是什么歌"：Bot 任务里也常出现这些词，所以**只有在放歌或暂停时**才算本地指令。
- 音量："音量调到三十""大声点""静音"。没在放歌时，必须带"音量"或"声"字才算。
- 前面有"别、不要、不用"的不算，"别放了"例外。

搜不到歌时：说法明显是在点歌（带"首、歌、我想听"等），就回答"没找到"；否则交给 Bot（例如"放到桌面上"）。

### 14.11 第二轮实机：改为"关键词加填充字"匹配（2026-10-22 晚）

**漏掉的两句。** 补完说法后，用户又在立创板上试了一轮，还有两句被交给了 Bot：
- "先给我暂停"：句首的"先"不在去掉的词里。
- "下下一首"：语音识别把"下"重复了一次。

**原因。** 按整句精确匹配，说法稍有变化就对不上。

**改法**（`localCommandHandle.py` 的 `KEYWORDS`、`FILLER`）

- **关键词加填充字**：句子里有控制词（暂停、停一下、继续、下一首、换首、跳过、上一首、从头、单曲循环、谁唱的、什么歌、关掉、别放了……），并且去掉控制词后剩下的只有填充字（先、给我、帮我、把、这首、歌、音乐、一下、吧、了……），就算这条指令。剩下的部分有实际内容，就不算指令，比如"暂停那个下载任务""把窗口关掉""从头开始讲一遍"。
- **重复的字**：识别结果里连续重复的字先合并（"下下一首"当作"下一首"）。
- **两种写法都匹配**：去掉句尾语气词之前和之后的写法都拿来匹配（"把音乐关了"）。判断否定（别、不要）时用原句（"别唱了"）。
- **"暂停"不再交给 Bot**：只要有歌（正在放、已暂停或刚放完），说"暂停"都在本机处理。

**验证**
- 单元测试 20 项，全部通过。
- 正在放歌时试了 30 句常见的 Bot 任务，没有一句被误认。
- 当晚识别出的 28 句里，有 4 句交给了 Bot。用新规则重新跑，这 4 句都能在本机执行。
- 后端已重启。

### 14.12 第三轮实机：歌名被识别错时按读音找（2026-10-22 晚）

**问题。** 实机说"帮我播放周杰伦的晴天"，语音识别成了"帮我播放周杰伦的**请帖**"：
- 本地指令匹配上了"点歌"，但搜不到《请帖》。
- 按原来的规则，搜不到、句子里又没有"首、歌"这类字，就当作不是点歌，交给了 Bot。

**改法**
- **按读音找**：说了歌手但搜不到这首歌时，把这位歌手在五个平台上的原版都列出来，用 `pypinyin` 比读音，挑最接近的一首。相似度要达到 0.75，并且字数一样；声母、韵母相近也算接近，比如 zh 和 z、an 和 ang。找到正确歌名后，再用它完整搜一遍，照常先搜网易云、再挑码率最高的。回复时会说明，例如"没找到请帖，给你放周杰伦的晴天"。
- **怎样算点歌请求**：说了"来一首、我想听"，或者句子里有"歌、首"，或者能在平台上找到这位歌手，就算点歌请求，搜不到时回答"没找到"。只说"播放……""放……"不算，所以"播放器怎么用""放到桌面上"还是交给 Bot。
- **新依赖**：`pypinyin` 0.55.0，MIT 许可，纯 Python。用 uv 装进了后端环境，也记进了本机的 `requirements-macos.txt` 和 lock 文件。没装这个库时，只是跳过按读音找这一步，其他功能照常。

**实测**（真实搜索，每句 1.5–2.7 秒）

| 识别结果 | 选中 |
| --- | --- |
| 周杰伦的请帖 | 晴天（咪咕） |
| 周杰伦的七里乡 | 七里香（咪咕） |
| 周杰伦的道香 | 稻香（咪咕） |
| 林俊杰的江男 | 江南（网易云） |
| 陈奕迅的孤用者 | 孤勇者（网易云） |
| 周杰伦的不存在的歌名 | 回答"没找到" |

**验证**：单元测试 22 项，全部通过。后端已重启。

**还没做**：没说歌手、歌名又识别错的情况（例如只说了"放请帖"）还不会按读音找。

### 14.13 第四轮：拆句、更多说法、提速、点歌热词（2026-10-22 晚）

**实机问题**

- 用户反馈：能用，但慢；走 Bot 也能放歌，只是更慢；语音识别问题多。

**匹配上的改动**
- **拆句**：按标点拆成几小句，逐句匹配。有一小句是指令，并且其余小句只是重复它，或者只是"播放、放、歌、音乐、随意、随便"这类词，就执行这条指令。"停一下，帮我看看下载任务"仍然交给 Bot。
- **"的"被识别成别的字**：搜索时允许把"在、得、地、之"当作"的"，但要用搜索结果核对，确认前面是歌手、后面是歌名。
- **新说法**：
  - "……的一首歌叫做 / 叫 / 名叫 X"：前面的"切换、另外、帮我"会去掉，只留下歌手名。
  - "换一首 / 再来一首 / 切换到 + 某某的歌"。
  - "某某的歌（随便放）"：当作放这位歌手的歌。

**速度**

实机日志里，语音识别每句只要 0.05–0.09 秒。慢在两处：
- EdgeTTS 联网合成回复，每句 1–3 秒。
- 点歌时先搜歌，搜完才合成回复。

改法：
- **点歌、下一首、上一首**：先说缓存好的"好的。""下一首。""上一首。"，同时去搜歌。歌一开始放，就把"正在播放：歌手的歌名"推到屏幕上，用 `bot_wait reply` 加 `tts sentence_start`，不再念出来。歌名被纠正或者没找到时，才另外说一句。
- **快进快退、音量**：只说"好的。"，具体数值显示在屏幕上。
- **固定短句提前合成**：板子连上时按使用频率依次合成 14 句；缓存在后端内存里，所有设备共用。
- **提前启动**：板子连上时，go-music-dl 和 mpv 就在后台启动。
- **同时搜**：说了歌手时，网易云和其他四个平台同时搜，网易云有就用网易云。

实测（模拟设备）：
- 暂停、继续、下一首、快进、从头播放、停止：说完后 **0.06 秒出声**，原来是 1–4 秒。
- 点歌：约 1.2–1.6 秒歌就开始放。
- 还慢的有两种情况：一是后端刚重启后的第一句（短句还没合成完）；二是"这是什么歌"，要现场念歌名，约 2 秒。

**语音识别**：本机点歌开着时，额外给 X-ASR 加 61 个热词：28 位常见歌手、23 首常被点的歌、10 个点歌指令词，热词总数从 23 个变成 84 个。配置里可以写 `local_music.hotwords` 追加自己的。热词只是让识别在读音相近的候选里偏向这些词，不会把没说过的词编出来。实机效果还要再看。

**验证**：单元测试 25 项（`test_local_music.py`）加 10 项（`test_asr_text.py`），全部通过；正在放歌时试了 36 句常见的 Bot 任务，没有一句被误认；当晚交给 Bot 或处理错的 9 句，用新规则重新跑，都在本机执行。

**没改的**：说完话后要静音 1 秒才算说完（`min_silence_duration_ms: 1000`），每句因此多等约 1 秒。10-21 改成 700 毫秒时，一句话会在中间停顿处被切成两句提交，所以先不动。
